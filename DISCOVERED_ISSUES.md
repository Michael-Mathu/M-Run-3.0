## From Phase 2 (`TS-9` — new unit tests for `ghost_race_utils.dart`)

5. **HIGH — `ghostExpectedTimeAtDistance()` in `app/lib/features/beat/ghost_race_utils.dart:6-29` overstates the ghost's elapsed time by roughly one split's duration for most of a race, not just at boundaries.** Root cause: when interpolating within split `lowerIndex`, it computes `lowerTime = splits.take(lowerIndex + 1)...` and `upperTime = splits.take(upperIndex + 1)...` — both sums *already include* the split the runner is currently inside of, instead of `lowerTime` being the cumulative time *before* entering it (`splits.take(lowerIndex)`). Verified with a flat 4-split, 100s/km ghost (`app/test/ghost_race_utils_test.dart`, tests tagged "KNOWN BUG"): at 500m of 4000m (12.5% done, should read ~50s), it returns **150s**; at the exact halfway point (2000m, should read 200s), it returns **300s**. Not fixed here — this task was scoped to adding test coverage, not changing behavior, and the fix affects a live, user-facing number people watch mid-run.
   - **User impact**: this feeds `GhostRaceController.update()`'s `deltaSeconds` (the "you're Xs ahead/behind" ghost-race comparison shown live during a run in `live_dashboard.dart`'s ghost chip, and the split table on `ghost_result_screen.dart` via `computeCurrentSplitComparison`, which also calls this function for `userSplitStartTime`). For most of a race, the app is currently telling users they're roughly one split *further ahead* of the ghost than they actually are — a real, visible correctness bug in one of the app's three headline features ("Beat Legends"), not a cosmetic one.
   - **Suggested fix**: change `lowerTime` to `ghost.splits.take(lowerIndex).fold(0.0, (a, b) => a + b)` (cumulative time *before* `lowerIndex`, i.e. drop the `+ 1`), keep `upperTime` as-is (cumulative time through `lowerIndex`), and interpolate with `t` as the fractional position *within* `lowerIndex`. Needs its own regression test asserting the corrected values (e.g. 500m → 50s, 2000m → 200s for the flat-ghost fixture) once the fix lands, and a check of whether `computeCurrentSplitComparison`'s own math still makes sense once its `ghostExpectedTimeAtDistance` calls return corrected values.

## From Phase 2 (`TS-6` — new unit tests for `gps_pipeline`)

6. **HIGH — `MatchQuality.evaluate()` in `packages/gps_pipeline/lib/src/match_quality.dart:28-99` computes `routeContinuityScore` wrong, causing `passesThresholds` to fail even for a perfect map-match.** `continuityTotal` is incremented in *both* the heading-agreement loop (lines ~50-51) and the separate route-continuity loop (line ~71), but `continuityPassCount` only ever accumulates from the second loop (line ~74) — the denominator counts contributions the numerator never had a chance to pass. Verified against the real implementation (not hand-derived) with `packages/gps_pipeline/test/match_quality_test.dart`'s "KNOWN BUG" test: a dead-straight, fully-matched (0 unmatched), high-confidence (0.9) 4-point route — every other `passesThresholds` input at its ideal value — still comes out `routeContinuityScore: 0.4` (2 passes / **5** total, should be 2/**2** = 1.0) and `passesThresholds: false`.
   - **User impact**: `MapMatchJob.processSession()` (`app/lib/features/tracking/map_match_job.dart`) rejects a match as `MatchStatus.rejectedLowQuality` whenever `!quality.passesThresholds`. With this bug, that threshold is behind an artificially low continuity score essentially all the time — even geometrically perfect matches routinely fail it. Combined with `SEC-4` (map-matching consent is currently disabled) and `DISCOVERED_ISSUES.md` #3 (nothing reads the match results anyway), this is a third, independent reason the map-matching feature isn't functioning as designed — worth fixing as one batch once `SEC-4`/#3 are resolved, since there's no point re-enabling the pipeline while its own quality gate is this broken.
   - **Suggested fix**: stop incrementing `continuityTotal` in the first (heading-agreement) loop — it already has its own `headingTotal` counter for that purpose. `continuityTotal`/`continuityPassCount` should only be touched in the second loop, which is the one actually named/intended for route continuity.

## From Phase 2 (`TS-4`/`TS-5` — wiring `synthetic_truth.ndjson` into an asserting test)

7. **MEDIUM, needs investigation — the pipeline's summed filtered/smoothed distance overshoots the synthetic ground-truth distance by ~45-50% on the checked-in fixture, despite good positional accuracy (mean deviation from truth: 4.26m, p95: 11.45m).** Measured via `packages/gps_pipeline/test/ground_truth_test.dart` against `test/fixtures/synthetic_raw.ndjson`/`synthetic_truth.ndjson`: `totalTruthDist=852.9m`, `filteredDist=1242.0m` (+45.6%). Re-ran with a freshly-generated fixture with stationary-stop density set to 0 (`tool/synthetic_runner.dart`'s `generateSyntheticRun(stationaryClustersPerKm: 0)`) to rule out stop-handling as the cause — **still ~50% overshoot** — so this isn't primarily a stationary-suppressor artifact. Most likely explanation: on a short (~850m), curvy, noisy course, summing point-to-point distance between ~150 smoothed-but-still-slightly-noisy points accumulates a "zigzag" overshoot that's a known characteristic of any point-to-point GPS distance summation (small residual lateral error at each point always *adds* length, never cancels), and this effect is proportionally larger on a short/curvy course than it would be on a longer, straighter real running route.
   - **Why this isn't fixed or asserted tightly here**: diagnosing and fixing cumulative-distance overshoot (vs. positional accuracy, which is already good) is a distinct, nontrivial pipeline-tuning problem — possibly needs path-length-aware smoothing or a minimum-segment-length/simplification pass, not a quick constant change. `ground_truth_test.dart` asserts a loose upper bound (`<60%`, current baseline ~45.6%) so it still catches a regression that makes this worse, without pretending the current number is validated as acceptable.
   - **Why this might matter for real users**: if this generalizes beyond the synthetic fixture's short/curvy course, it suggests the app's reported run distance could be measurably inflated versus true distance — a real accuracy concern for a running-tracker's core metric. It might *not* generalize much (real routes are typically longer/straighter, diluting the effect), but that's an assumption, not something verified here. **Suggested next step**: generate a longer (5km+), straighter synthetic course with `tool/synthetic_runner.dart` and re-run this comparison — if `distErrPct` drops to low single digits there, this is mostly a short-course artifact and low priority; if it stays high, this needs real investigation, likely starting with `packages/gps_pipeline/lib/src/kalman_filter.dart`'s process-noise tuning or adding a post-hoc route-simplification step.

## From Phase 3 (`CQ-9` — deferred, not attempted in full)

8. **`TrackingModel` (`app/lib/features/tracking/tracking_controller.dart`) has no seam for testing its GPS-engine-coupled paths.** `start()`/`resume()`/point-processing all call directly into a concrete `MwendoGpsEngine()` instance (`final _engine = MwendoGpsEngine();`), constructed inline rather than injected. This blocks writing unit tests for the state machine (idle → recording → paused → recovering transitions, point accumulation, pause/resume timing) without a real device/emulator or platform-channel mocking neither available in a plain `dart test`/`flutter test` run. It's also *why* `CQ-9`'s full "split into focused services" restructuring wasn't attempted this session — no safe way to verify the split preserved behavior on these paths. **Suggested fix**: extract an abstract `GpsEngine` interface (already conceptually thin — `startRecording()`, `pause()`, `resume()`, `stop()`) that `TrackingModel` takes as a constructor/provider parameter, defaulting to a real `MwendoGpsEngine()` in production and swappable for a fake in tests. That single seam would unblock both real unit tests for `TrackingModel` and a much lower-risk attempt at the full `CQ-9` split later.

## From Phase 5 (`UX-4` — ghost-result share button) — RESOLVED

9. ~~**`ghost_result_screen.dart` used the localization key `'ghost_held_you_off'`, which was never defined in `app_strings.dart`.**~~ **Fixed.** `L10n.tr()` falls back to returning the raw key string when a key isn't found (`app_strings.dart:367`, `_strings[key]?[lang] ?? _strings[key]?['en'] ?? key`), so every time a user *lost* a ghost race, the result screen's headline literally displayed the text `"ghost_held_you_off"` instead of a real sentence — silent because it's a runtime map lookup, not a compile error, and nothing exercised the loss branch in a test before now. Added the missing key (`'en': 'The ghost held you off!'`, `'sw': 'Mzuka amekuzuia!'`). Covered by the new `app/test/ghost_result_screen_test.dart`.

10. ~~**The ghost-result header (`SliverAppBar`, `expandedHeight: 280`) overflows on realistic phone widths when the headline text is long enough to wrap to two lines.**~~ **Fixed.** Discovered via the same test file: at a 375px-wide viewport (an iPhone SE-class width), the loss headline ("The ghost held you off!") wraps to two lines and the fixed-height header overflows by 59px — a real, visible layout bug (not just a test artifact; confirmed the overflow scales with viewport width, worse on narrower phones, and was present before this session's `ghost_held_you_off` fix too, just harder to trigger since the fallback raw-key text happened to be short enough to fit on some widths). Fixed by increasing `expandedHeight` to 320, switching the headline from `displaySmall` to the smaller `headlineMedium`, reducing a fixed top spacer, adding horizontal padding so text wraps before hitting the screen edge, and capping the headline at `maxLines: 2` with `TextOverflow.ellipsis` as a hard backstop against any future long string (e.g. a longer Swahili translation) overflowing again. Regression-tested at both the default wide test canvas and a realistic 375×812 phone size.
